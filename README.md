# NOTBAD Attendance MVP

NOTBAD 스포츠 클럽의 일정 생성, 참석 신청, 운영진 출석 확정, 월별 참석 현황을 다루는 첫 번째 웹 MVP입니다.

## 현재 동작

- 회원 가입 및 운영진 회원 추가
- 이름 + 6자리 PIN 로그인
- 신규 회원은 가입 요청 후 운영진 승인 필요
- 운영진 화면에서 가입 요청 승인/거절
- 관리자 `admin` 계정은 회원을 운영진으로 지정/해제 가능
- 회원은 건의사항 페이지에서 개선 제안, UI/UX 불편, 버그를 제출
- 운영진은 건의사항을 확인하고 상태를 변경
- 모든 회원의 일정 생성
- 일정별 선택값으로 최소 인원과 자동 취소 시각 설정
- 일정별 `참석 / 미정 / 불참` 신청
- 자동 취소 시각 이후 참석 신청 수가 최소 인원보다 적으면 삭제하지 않고 `취소됨`으로 잠금
- 일정 종료 후 운영진이 실제 출석자를 체크하고, 운영진 2명이 승인하면 확정
- 확정된 출석만 개인 월간 참석 횟수에 반영
- 요약에서 전체 다음 일정과 내가 참석 신청한 다음 일정을 분리 표시
- 대시보드 일정을 전체, 대기중, 취소됨, 완료됨 상태로 필터링
- 대시보드 월별 조회와 특정 날짜만 보기
- 운영진 월별 참석표와 CSV 다운로드
- 운영진 출석 확정 목록은 확정 필요, 진행 예정, 확정 완료 상태별로 필터링
- 출석 확정 전 명단이 바뀌면 기존 운영진 승인은 초기화
- 운영진 월별 참석표는 일별 참석 횟수와 합계로 집계
- 카카오톡에 붙여넣기 쉬운 일정 공유 문구 복사
- 일반 회원은 본인 참석 상태와 월간 출석만 접근, 운영진만 전체 월별 현황 접근
- 일정 수정/삭제는 작성자와 운영진만 가능

## 실행

Vite 기반 프론트엔드 앱입니다.

```bash
npm install
npm run dev
```

그 다음 터미널에 표시되는 로컬 주소로 접속합니다. 배포용 파일은 아래 명령으로 생성합니다.

```bash
npm run build
```

## Supabase 준비

Supabase 프로젝트를 만든 뒤 SQL Editor에서 `supabase/schema.sql`을 실행합니다.
Vercel에는 아래 환경변수를 등록합니다.

- `VITE_SUPABASE_URL`
- `VITE_SUPABASE_ANON_KEY`

로컬 개발에서는 `.env.example`을 참고해 `.env.local`을 만들면 됩니다. 환경변수가 없으면 기존처럼 브라우저 `localStorage`로 동작하고, 환경변수가 있으면 Supabase에서 먼저 데이터를 불러온 뒤 저장 내용을 DB에 반영합니다.

새 Supabase DB가 기본 관리자 `admin`과 운영진 `쥬스`만 가진 상태이고 현재 브라우저에 기존 일정/회원 데이터가 있으면, 첫 실행 때 그 로컬 데이터를 Supabase로 올립니다.

현재 SQL 정책은 MVP 연결 확인용으로 넓게 열려 있습니다. 이 상태의 Supabase 환경변수를 공개 배포에 연결하지 마세요. 실제 운영 보안은 Supabase Auth 또는 Edge Function 기반 서버 검증과 RLS 정책으로 좁혀야 합니다. 아직 Auth/Edge Functions를 붙이지 않았다면 `supabase/lockdown.sql`을 실행해 공개 읽기/쓰기를 막아야 합니다. 지금 구조는 여러 사용자가 동시에 수정할 때 마지막 저장이 이기는 단순 동기화 방식입니다.

## 초기값

- 클럽 이름: `NOTBAD`
- 관리자: `admin`
- 운영진: `쥬스`
- `admin`, `쥬스` 계정은 첫 로그인 때 입력한 PIN으로 초기 설정
- 회원 PIN은 6자리 숫자
- 출석 카운트 기준: 일정 완료 후 운영진 2명이 승인한 실제 출석

## 다음 단계

로그인 세션은 브라우저 `localStorage`에 저장됩니다. 데이터는 Supabase 환경변수가 있으면 DB에 저장되고, 없으면 브라우저 `localStorage`에만 저장됩니다. 이 MVP에서는 화면과 동작을 계정별로 제한하지만, 실제 보안은 Supabase Auth 또는 Edge Function 기반 서버 검증과 RLS 정책이 필요합니다.

이름 + 6자리 PIN을 프론트엔드만으로 처리하면 Supabase RLS가 실제 운영진 여부를 신뢰할 수 없습니다. 회원 공개 전에 운영진 승인, 출석 확정, 회원 삭제 같은 쓰기 작업은 Supabase Auth 또는 Edge Function 뒤로 옮겨야 합니다.

자동 취소도 현재는 앱이 열려 있거나 다시 열릴 때 브라우저에서 평가합니다. 실제 배포판에서는 서버 작업 또는 Supabase Edge Function/cron으로 같은 규칙을 실행하는 편이 안전합니다.

권장 전환 순서:

1. Supabase 프로젝트 생성
2. `supabase/schema.sql` 실행
3. Vercel에 `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY` 등록
4. Supabase Auth 또는 초대 링크/카카오 로그인 연결
5. 운영진 권한을 RLS 정책으로 강제
